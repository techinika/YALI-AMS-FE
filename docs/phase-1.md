## Schema decisions

- **Profiles keyed to `auth.users.id`.** Password/tokens stay in `auth.users`;
  `middle_name`, `phone`, `whatsapp` are nullable; role is an enum; status is an
  enum.
- **Unified chat model.** `conversations` + `conversation_members` +
  `messages` covers community, private 1:1 and group chats. This gives one RLS
  pattern and one Realtime stream, and removes the legacy `Message.public` flag
  and `userId`-in-URL authorization holes.
- **Group approval workflow** lives in `conversation_members.status`
  (`admin_approval_pending`, `member_joining_pending`, `approved`, ...).
- **Unread chat counts** are supported by `conversation_members.last_read_at`;
  the client will update it through an RPC in Phase 4.
- **Phone/WhatsApp private by default.** Stored on `profiles` but not directly
  selectable; `get_profile_contact()` returns them only for the owner, an admin,
  or when the owner opted in.
- **Privilege escalation blocked.** `role`, `status`, `email`, `embedding` and
  `search_text` are not client-updatable (column privileges + RLS).
- **Reminder cron.** `generate_profile_update_notifications()` replaces the
  `node-cron` job: 6-month stale profiles, at most one reminder per 24 h,
  scheduled hourly with `pg_cron`.

## Seed data

`supabase/seed.sql` is generated by `scripts/generate-reference-seed.mjs` and
committed so `supabase db reset` needs no Node runtime or network.

- 250 countries (+ `unspecified`)
- 5 Rwanda provinces, 30 districts + `unspecified`
- **416 Rwanda sectors** (derived correctly; the legacy `rwanda` helper returned
  province-wide sectors for every district, which is why the old DB had 2,696
  duplicate sector rows)
- 4 genders, 56 cohorts, 4 tracks, 25 working sectors
- 3 notification templates (`signup`, `update`, `updated`)
- singleton community conversation (`00000000-0000-0000-0000-000000000001`)

## Validation performed

1. **Syntax:** all 11 migrations parsed with `libpg-query` (PostgreSQL 18 grammar) — 0 errors.
2. **Semantics:** applied all migrations + seed to a live PostgreSQL 18 cluster
   (with `vector` replaced by `text`, HNSW index lines omitted, and minimal
   `auth`/`storage` stubs) — all statements succeeded.
3. **Trigger:** inserting into `auth.users` creates the `profiles` row with the
   correct role/status; an auth update that does not change email does not bump
   `profiles.updated_at`; an email change syncs `profiles.email`.
4. **RLS:** verified with three users (Alice, Bob, Carol) and an admin:
   - direct `phone`/`whatsapp` select is denied; `get_profile_contact` returns
     the owner's own contact and another user's only when opted in;
   - cross-profile update affects 0 rows; changing own `role` is denied;
   - Carol cannot read a private conversation or its messages;
   - Carol can see a group where she is `admin_approval_pending`, but not its
     messages;
   - Carol cannot insert into a private conversation;
   - notifications are visible/owned per receiver;
   - non-admins see 0 activity logs / matchmaking requests / import jobs;
   - `generate_profile_update_notifications()` inserts once and is suppressed
     within 24 hours.
5. **Types:** generated `supabase/types/database.ts` from the validated schema
   with `supabase gen types typescript --remote=<db-url> --schema public`.
